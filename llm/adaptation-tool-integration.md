# 第三方适配工具接入计划

把成熟工具的能力接到识别、提取、回填和试译流程中。识别优化以相同覆盖范围的正确文本可供试译为终点，优先消除模型找工具、猜格式、写临时探针和反复解包的工作。接入按能省掉的工作量和证据强度排序。

默认复用能单独调用的格式规则、解析模块或命令行能力。带 GUI 的项目可提供实现参考和人工比对结果。自动流程使用固定版本的无界面入口。

## 一次交付的范围

同一次交付完成共用接入、选定格式的适配、发行包验证和收益验收。逐项核对六个项目的能力与现有覆盖，对每个准备采用的格式明确版本、识别证据、能完成的操作、补丁加载方式、固定依赖和验证样本。具备从识别到补丁运行证据的路线可进入正式支持。仅能确认资源结构或提取小样的能力登记为调查工具，并把剩余缺口交给现有适配流程。已有等效能力时沿用现有实现。

以真实高消耗案例中能省掉的工作量确定覆盖范围。覆盖外的格式和变体仍可通过现有调查、组件调用和适配器验证入口处理。格式专用条件尽量由现有组件注册、识别声明或适配器表达，使同类资源可以复用整条流程。[识别声明](../docs/adapters/recognition.md) · [适配器协议](../docs/adapters/protocol.md)

优先打通 PFS v8 与 Artemis AST 的适配链路。现有小样已经能定位脚本，主要缺口是把完整资源上的文本、姓名和控制命令稳定映射到回填结果，并保留未改成员。BGI、普通 KIF 和已确认索引布局的 YPF 共用按成员读取入口，写入能力按格式的验收范围登记。

## 技术路线

优先用 Rust 实现自研原生工具和运行组件。已有 Python 解析器、规则和适配入口通过便携 Python 直接复用。确有必要时沿用现有 C# NativeAOT 工具及构建链。独立原生工具通过现有进程接口接入，正式适配入口保持 Python。

默认使用当前 Cargo、便携 Python 和已有 NativeAOT 构建入口。引入其他技术方案、新的第三方运行 DLL、额外工具链或系统运行时前，先提交适用样本、预期收益、现有技术路线的局限及构建、打包和维护成本，供项目维护者确认。自动流程的依赖通过现有工具准备、发布和固定版本机制提供。[开发和构建](../docs/development.md#工具准备) · [构建脚本](../scripts/prepare-tools.ps1)

## 接入位置

| 层级 | 适合推进的能力 | 进入自动流程的依据 |
| --- | --- | --- |
| 跨引擎 | 同一份资源清单筛选封包，按需读索引和成员，复用解析器小样验证，向模型提供简短的结果 | 资源证据足以选择有限的候选，探测成本可控，已支持游戏和未命中游戏依然能快速继续 |
| 引擎家族 | 复用已经存在的「封包读取器 → 脚本解析器」，按布局组合资源选择、构建和验收方式 | 可识别的格式与版本证据，代表性样本的提取和往返通过 |
| 特定引擎或变体 | 补充私有过滤器、脚本指令、伴随文件、编码或补丁加载方式 | 有真实样本能复现缺口，确认适用条件后再登记，运行时效果按游戏试译确认 |

1. 先走已有适配器复用和本地模板路径。需要调查封包时，用同一份资源清单和文件头、索引结构及伴随文件筛选有限候选。沿用 `run_engine_component` 的 `inspect` / `extract` 入口，读取索引后只选少量完整脚本和所需伴随文件。大包首先按范围读取，限制成员数、解码量和耗时。目录未命中或样本结构不符时继续现有候选流程。[封包组件](../docs/adapters/templates.md#封包组件)
2. 复用 `try_builtin_adapter` 或固定的第三方模块检查提取、原文往返和少量中文回读。继续使用 EAGLS SCPACK 和 Artemis PFS v8 已有的首轮样本结果机制。模型只需要看到匹配证据、样本位置、验证阶段和具体失败原因。已完成试验可沿用现有会话记录，资源、伴随文件、工具版本或关键参数变化时重新确认。[自动试用](../crates/engines/src/adaptation_automatic.rs) · [小样工具](adapter-development.md#内置脚本解析器)
3. 匹配已有模板时沿用正式适配和验收。部分命中时把已通过的结果和缺口交给模型，例如封包能读且原文可回填，中文编码仍需验证。提取结果按原资源和脚本位置映射到适配器协议，核对正文、姓名、选项、控制标记及文本覆盖。正式验收保留既有文本 ID、译文和未修改数据。[智能适配验收](../docs/adapters/automatic-adaptation.md#验证与产物)
4. 在选定游戏上确认写回路径。有可用写入器时以 `replace` 重建并复提，保持原成员标识和未改动成员的内容。有实际加载顺序和覆盖证据时以 `overlay` 仅构建变更文件，合并原资源和补丁做复验。含多卷、重名成员或伴随文件时核对实际加载结果。只能稳定读取时保留有依据的小样和具体写回缺口，供现有调查流程使用。[构建与校验](../docs/adapters/protocol.md#构建与校验)
5. 编码、字体、代理和加载工具在具体试译或修复中按需选用。用正常补丁入口验证生成、安装、游戏内显示和恢复原版，并记录运行确认。衡量这些工具省掉的运行问题调查和返工。[运行组件](../docs/adapters/components.md) · [安装和恢复原版](../docs/data-storage.md#安装和恢复原版)

## 需要核对的格式路线

这些组合涵盖现有快路径、可复用的读写能力以及最容易遗漏的写回条件。实际纳入的变体以固定样本和验收结果为准。

| 格式 | 可用基础 | 交付前确认 |
| --- | --- | --- |
| Ren’Py RPA3 / RPYC2、KiriKiri XP3 | 已有模板和 SMIL 适配器 | 复用路径、混合资源加载根、XP3 过滤器判定和原有文本身份继续通过验证 |
| EAGLS SCPACK、Artemis PFS v8 | 已有首轮小样，Artemis 有覆盖卷参考 | 新接入复用已有小样和候选。Artemis 核对部分回填的小样复测和多卷覆盖条件 |
| BGI PackFile / BURIKO ARC20 → Ethornell | 固定库已有按范围读取、DSC 处理和写回器，VNTextPatch 已有脚本解析器 | 代表性封包可只取脚本小样，重建复提匹配，CP932 脚本的运行显示有依据 |
| CatSystem2 KIF / INT → CST | 固定库已有读取器，VNTextPatch 已有 CST 解析器 | 分别确认普通与加密变体的读取条件和写回去向。GARbro 的写入器产生普通 KIF，msg-tool 当前提供读取。需要写回加密包或通过覆盖加载的情况以实机证据为准 |
| YU-RIS YPF → YBN | 固定库提供选择性读取及特定版本写入，VNTextPatch 已有 YBN 解析器及 SJIS 隧道支持 | 核对封包版本、同目录命令表、补丁加载和映射稳定性 |

## 各项目的接入方向

### GARbro

优先复用格式签名、索引读取和指定成员的解压逻辑。现有固定工具库已经能按索引读取 BGI、CatSystem2 等封包成员，可先接到通用探测入口，再交给已有脚本解析器。BGI ARC → Ethornell 可作为验证串联方式的样板。真实收益优先在仍需多轮拆包调查的项目上验证。[现有工具库](adapter-development.md#引擎资料与额外依赖) · [内置解析器](../docs/adapters/engines/vntextpatch.md) · [GARbro 格式表](https://morkt.github.io/GARbro/supported.html)

对于现有实现缺失或确有读取瓶颈的格式，按格式选取 GARbro 的核心实现，作为独立 Rust 工具的参考。移植从只读探测、列成员和按需提取开始，使用现有进程接口和只读输入。真实样本与 GARbro 对照成员名、大小及解包字节。需要 `Formats.dat` 的变体按证据整理成明确的数据字段。原版源码约 24 万行 C#，其中声明归档处理器的文件约 9.7 万行，移植优先按新增覆盖和实际耗时收益取舍，并保留适用许可。[固定源码](https://github.com/morkt/GARbro/commit/b09ee4570ccb1daf6ac56710ee8934dc0b8baeb0) · [格式与方案数据](https://github.com/morkt/GARbro/blob/b09ee4570ccb1daf6ac56710ee8934dc0b8baeb0/GameRes/FormatCatalog.cs) · [MIT 许可](https://github.com/morkt/GARbro/blob/b09ee4570ccb1daf6ac56710ee8934dc0b8baeb0/LICENSE)

### msg-tool

优先评估能补上现有脚本读写缺口的格式。选定格式后，用固定的 Rust CLI 对单脚本或工作副本中的小样调用 `export` / `import`。使用 `--exit-code` 和 `--exit-code-all-failed` 明确返回失败，核对结构化输出和生成文件。其 `unpack` 以整包输出为主，适合有界的工作副本或确需整包处理的情况。构建时只启用实际需要的格式特性，选择性读成员有明显收益时可复用对应的 Rust 核心。正式采用前验证导出结构、回填身份、编码和 GPL-3.0-or-later 条款。[固定版本文档](https://github.com/lifegpc/msg-tool/blob/v0.4.0-alpha.3/README.md) · [解包接口](https://github.com/lifegpc/msg-tool/blob/v0.4.0-alpha.3/src/args.rs) · [构建特性和许可](https://github.com/lifegpc/msg-tool/blob/v0.4.0-alpha.3/Cargo.toml)

### SExtractor

优先复用明确格式的解析和回填模块，或抽取能稳定识别对白、姓名、选项的正则预设。通过现有便携 Python 执行小型适配层，显式提供编码、规则和本次文件的状态，按脚本位置保留稳定的文本身份和控制标记。上游静默提取仍需启动 Qt，复用应落在具体的解析模块、预设或封包脚本。二进制启发式匹配的结果用作线索，进入正式适配需要格式证据和往返验收。核对当前 Python 版本及所选模块的依赖和 GPL-3.0 条款。[处理规则](https://github.com/satan53x/SExtractor/blob/8d8d976fd04ae54e7c677705af937273d04a376a/README.md) · [程序入口](https://github.com/satan53x/SExtractor/blob/8d8d976fd04ae54e7c677705af937273d04a376a/run.py)

### KirikiriTools

常见 KS 的去混淆沿用内置 VNTextPatch，选择性提取标准 XP3 和受支持的 SMIL 变体已有组件。对具体未覆盖的脚本包装层，可复用去混淆核心接回现有脚本解析器。静态流程无法确认资源或补丁加载时，以其运行期读取与覆盖能力作为参考，采用新的运行组件前按技术路线确认。试验使用游戏副本，核对主要文本覆盖、补丁优先级和 DLL 冲突。运行期观察的证据范围限于实际访问的成员。[现有 KS 解析器](../third_party/VNTextPatch/Scripts/Kirikiri/KirikiriKsScript.cs) · [SMIL 支持](../docs/adapters/engines/kirikiri-smil-smile.md) · [KirikiriTools](https://github.com/arcusmaximus/KirikiriTools/blob/9590c3cce4733e1f048cd407bfb57e8ce71f1f95/README.md)

### VNTextProxy

当 CP932 脚本需要 SJIS 隧道时，沿用现有固定 x86 代理和映射组件，生成稳定映射并准备匹配的运行文件。用试译核对实际加载的代理、保留原文、中文显示、字体和换行。将已验证的配置纳入该适配器的运行依赖。[现有代理组件](../docs/adapters/components/vntextproxy-runtime.md) · [上游固定版本](https://github.com/arcusmaximus/VNTranslationTools/blob/v0.0.41/README.md#vntextproxy)

### UniversalInjectorFramework

作为已定位的 Windows 文字处理、字体选择或文件加载问题的诊断参考。现有组件优先用于补丁交付。采用 UIF 运行库须有额外收益的实机证据、明确的分发条件，并按其他接入方案确认。自备工具的按需试验只使用必要的 JSON 配置子集，核对游戏实际使用的 API、位数和代理冲突。[上游配置手册](https://github.com/AtomCrafty/UniversalInjectorFramework/blob/80c46c381643e217fa26de5749e4d3efcf9c69f8/README.md)

## 工具环境与发布

- 复用共享工具库、便携 Python、原生工具准备和现有进程隔离。将上游源码、固定归档或版本记录放在 `third_party/`，自研原生工具用 Rust，分析与适配入口继续使用 Python。自动探测使用本机已准备的工具。正式依赖记录来源、版本、哈希及许可，按对应条款提供源码与声明，通过现有发布机制固定版本。[适配工作区与发布清单](../docs/adapters/artifacts.md)
- 静态工具读取宿主授权的输入。支持只读句柄的读包器可直接做随机访问。仅支持文件路径的外部工具使用受限的工作副本，并把复制成本纳入试验。输出写入工作区，校验成员路径、输出大小、退出状态和生成文件，沿用超时和取消。可选调查工具缺失时返回原因并沿用现有调查路径，正式适配器的依赖或访问失败按现有协议处理。[执行隔离](../docs/adapters/execution-isolation.md) · [错误语义](../docs/adapters/protocol.md#请求与结果)
- 新接入的无界面工具在 Windows SSH 下验证静态读写和失败处理。需要桌面组件的端到端检查及游戏显示、代理和补丁加载在交互式环境验收。发布包登记相应适配器实际使用的模块、工具及许可。[开发校验](../docs/development.md#检查)

## 完成条件

在同一次交付内先固定覆盖和验收样本，再打通共用流程、补齐选定的读写缺口，并验收以下结果。

| 场景 | 验收结果 |
| --- | --- |
| 正常入口 | 从“识别游戏”可到达新能力。已验证的模板走现有资源验收，需要调查时首轮可直接使用已有的探测和小样证据。常规识别、强制智能识别及修复分别保留各自的入口语义 |
| 识别失败与续接 | 误后缀、未支持变体、缺伴随文件和可选工具失败有明确去向，探测和解压工作有上限。取消、续接、重复识别及输入变化能复用或重建正确的结果 |
| 正式适配和补丁 | 纳入正式支持的每条路线有真实样本，完成同范围提取、原文往返、部分及完整译文复提。旧项目保留文本 ID、译文和固定依赖。可运行补丁通过加载、中文显示和恢复检查 |
| 构建与分发 | 用现有脚本在干净的开发环境准备工具并打包。通过发行版验证解析、回填和缺依赖诊断，记录采用的源版本、哈希、许可和适用范围 |
| 识别收益 | 固定资源、模型和验收目标，回放实际高消耗案例。证实同范围文本更快可供试译，模型消耗下降，并明确省掉的调查或重复处理步骤。记录耗时、请求数、输入、缓存和输出 Token。用已支持和未知格式作对照，核对旧的快速复用路径和未命中时的探测开销 |

工具逐项形成实际采用、复用现有能力或作为调查参考的结论。仅适用于已验证范围的能力按相应范围登记。已有工具覆盖充足、收益很小或主要瓶颈在模型理解时，采用现有路径并记录判定依据。[衡量方法](recognition-efficiency.md#衡量结果) · [版本反馈与修复](../docs/adapters/automatic-adaptation.md#版本反馈与修复)
