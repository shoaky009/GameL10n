# 基于真实游戏的识别优化自动化方案

输入是一个游戏安装目录，输出是一份简短的提升报告。设计目标是让智能体调用 GameL10n 的识别接口、等待结果、诊断消耗，并用同一游戏验证值得保留的改动。优先寻找能省去整段模型调查的机会，尤其关注同一家族换版本后重新解包、研究脚本或实现回填的情况。

## 一次实验

1. **运行基线。** 在独立的实验数据目录中登记游戏，记录程序提交、模型配置、预算、初始适配器库和经验库。从普通“识别游戏”入口启动，让已有适配器、本地试验和智能适配按产品顺序运行。实现时可给 Core 的识别接口补一个只执行识别、返回任务终态的 CLI 入口。[Core 识别入口](../crates/core/src/engine_tasks.rs) · [现有 CLI](../crates/core/src/main.rs)
2. **等待并保留证据。** 跟踪任务至完成、失败、需要人工输入或预算用尽。临时网络和响应格式错误沿用应用的重试逻辑。在实验预算内续接时，合计各次运行的请求与用量。清理前将诊断所需的日志、运行标识、提取来源和验收结果保存在待清理项目目录之外。[日志诊断](../.agents/skills/review-adaptation-logs/SKILL.md) · [消耗指标口径](../docs/consumption-metrics.md)
3. **决定是否改动。** 沿日志找出首次出现关键证据的轮次、随后模型做了什么，以及直到下一次有效验收花了多少请求和 Token。若本地已有足够证据直接完成一段工作，写清哪项改动可以省掉它、适用于哪些输入、实现和维护成本如何。只有明确的大收益才进入实现。收益小而改动大，或证据只够说明“这次很贵”，到此出报告。
4. **实现后从头重跑。** 将改动放入共享流程、引擎家族组件或具体格式变体中实际负责该行为的位置。使用同一游戏资源、模型配置、预算和验收目标，清理本轮生成的实验项目数据，再以改后程序重新登记并识别。两轮从同一份初始库出发，避免基线刚发布的适配器或经验直接命中复测。清理范围仅限实验数据，原游戏和日常项目库均在范围之外。
5. **核对收益。** 对照到达同一验收阶段的请求数、总 Token、未缓存输入和输出 Token，耗时作为补充。核对主要文本来源、文本 ID、原文往返和实际译文写回。用量缺失时标明已知范围。若基线耗尽预算而复测完成，报告两轮实际消耗和各自到达的阶段，节省比例留空。

## 同家族换版本时如何复用

按可验证的能力拆分。封包索引、脚本解码、文本提取、译文回填和整卷重建可以分别用本地小样验证。遇到新版本，把已通过的步骤、对应样本和第一个失败点交给模型，使调查从实际差异开始；发布前仍执行完整验收。

例如 QLIE 3.0 和 3.1 共享 ImoScripter 脚本处理，但索引与密钥布局不同。后续版本如果能沿用脚本提取和回填，只有封包重建失败，就保留这些已验证能力，集中处理重建差异。版本号可作为线索，适用条件由资源结构和读写结果确定。[QLIE 模板与验收范围](../docs/adapters/engines/qlie-filepack3-systemfont.md)

有同家族相邻版本样本时，检查旧版本仍能通过，并观察另一版本能否跳过同一段模型调查。只有一个游戏样本时，收益结论限定在该游戏，报告中注明待验证的版本范围。

## 提升报告

- **结论**　保留改动、放弃改动，或本轮没有值得实施的优化。
- **原因**　指出消耗最大的可避免工作、支撑判断的日志位置，以及实际省掉的步骤。
- **对照**　列出基线和复测的消耗、终态和验收范围。仅做了基线时写明停止原因。
- **适用范围**　列出已验证的游戏或格式版本、可复用的能力，以及仍需样本验证的差异。
