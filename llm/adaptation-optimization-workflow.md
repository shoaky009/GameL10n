# 基于真实游戏的识别优化自动化方案

输入是一个游戏安装目录，输出是一份简短的提升报告。设计目标是让智能体调用 GameL10n 的识别接口、等待结果、诊断消耗，并用同一游戏验证值得保留的改动。优化原则是**沉淀可拆装的底层积木、共用流程改进与避坑线索，同时保留智能体处理未知变体的自由度**——不把特定引擎做成封闭白名单或一刀切的最终适配器。

## 一次实验

1. **运行基线。** 在独立的实验数据目录中登记游戏，记录程序提交、模型配置、预算、初始适配器库和经验库。从普通“识别游戏”入口启动，让已有适配器、本地试验和智能适配按产品顺序运行。实现时可给 Core 的识别接口补一个只执行识别、返回任务终态的 CLI 入口。[Core 识别入口](../crates/core/src/engine_tasks.rs) · [现有 CLI](../crates/core/src/main.rs)
2. **等待并保留证据。** 跟踪任务至完成、失败、需要人工输入或预算用尽。临时网络和响应格式错误沿用应用的重试逻辑。在实验预算内续接时，合计各次运行的请求与用量。清理前将诊断所需的日志、运行标识、提取来源和验收结果保存在待清理项目目录之外。[日志诊断](../.agents/skills/review-adaptation-logs/SKILL.md) · [消耗指标口径](../docs/consumption-metrics.md)
3. **决定是否改动。** 沿日志找出首次出现关键证据的轮次、随后模型做了什么，以及直到下一次有效验收花了多少请求和 Token。优先判断能否把高成本或高暗坑步骤拆成**独立可复用的组件/诊断线索**，并检查改动是否会收窄智能体应对未知变体的自由度：组合模板只作已确认高频布局的快捷通道，未命中时平滑交回智能体；宿主只硬拒已证实的错误，不对“尚未登记的新变体”设阻断门禁。只有明确大收益且不破坏开放性的改动才进入实现；收益小而改动大、或只对单个游戏特例有效时，到此出报告或沉淀为经验线索。
4. **实现后从头重跑。** 将改动放入共享流程、正交引擎组件或经验参考中实际负责该行为的位置。使用同一游戏资源、模型配置、预算和验收目标，清理本轮生成的实验项目数据，再以改后程序重新登记并识别。两轮从同一份初始库出发，避免基线刚发布的适配器或经验直接命中复测。清理范围仅限实验数据，原游戏和日常项目库均在范围之外。
5. **核对收益。** 对照到达同一验收阶段的请求数、总 Token、未缓存输入和输出 Token，耗时作为补充。核对主要文本来源、文本 ID、原文往返和实际译文写回，并检查对同家族未知变体不会新增硬拒门禁。用量缺失时标明已知范围。若基线耗尽预算而复测完成，报告两轮实际消耗和各自到达的阶段，节省比例留空。

## 同家族换版本时如何复用

按可验证、可独立组合的能力拆分（封包索引/重建、脚本解码/提取/回填、字体/字形与启动组件）。遇到新版本时，快捷模板若未完全命中，把已通过的小样步骤、可复用的底层组件、第一个失败点和避坑线索交给模型，让智能体从实际差异自由实现剩余层，而不是要求宿主先登记该版本才能继续；发布前执行通用完整验收，并由实机试译闭环确认最终显示。

例如 QLIE 不同版本可能变换尾表、密钥、脚本方言或字体配置布局，但底层的衍生字体、启动器或部分脚本规则仍可单独复用。版本号仅作线索，适用条件由资源结构和实测结果确定；宿主未登记的新尾表或新方言应标明待实机确认的缺口并允许试译，而非阻断自定义适配器。[QLIE 模板与验收范围](../docs/adapters/engines/qlie-filepack3-systemfont.md)

有同家族相邻版本样本时，检查旧版本仍能通过，并观察另一版本能否跳过同一段模型调查。只有一个游戏样本时，收益结论限定在该游戏，报告中注明待验证的版本范围。

## 提升报告

- **结论**　保留改动、放弃改动，或本轮没有值得实施的优化。
- **原因**　指出消耗最大的可避免工作、支撑判断的日志位置，以及实际省掉的步骤。
- **对照**　列出基线和复测的消耗、终态和验收范围。仅做了基线时写明停止原因。
- **适用范围**　列出已验证的游戏或格式版本、可复用的能力，以及仍需样本验证的差异。
