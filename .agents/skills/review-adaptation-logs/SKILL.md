# 智能适配日志诊断

命令在仓库根目录执行，复用 `scripts/analyze-adaptation-log.ps1`。本技能供开发维护按需调用，游戏分析模型的运行时提示词独立维护。

## 诊断结论

默认读者已经看到项目进度、结果和消耗摘要。直接用通俗的话回答哪里慢、为什么慢。有明确收益时把改法和原因写在一起。主要耗时来自必要工作、当前模型或服务等待时，可以直接给出这个结论。没有发现值得改的项目环节时就如实说明。证据不足时说清哪些原因尚未确认。项目状态、用量、耗时明细、日志路径和证据位置留在内部取证，用户明确询问时再补充。

取证时沿运行里程碑定位消耗，核对哪些工作推动了进展，哪些结果可以复用。Token 看请求次数、缓存与未缓存输入和输出，时间看墙钟耗时及其中的调度等待、API、本地工具和验收。嵌套或并行的计时按实际经过时间判断。比较项目改动时尽量固定输入、模型配置和验收里程碑，区分实测结果、推测原因与预计收益。

## 先取摘要

```powershell
.\scripts\analyze-adaptation-log.ps1 -ProjectDirectory '<项目目录>'
```

默认读取截止调用开始时的日志，输出紧凑 JSON：已记录的 Token、失败与缺失计数、最近六次运行、最后源码修改和验收、耗时与输出最大的工具及少量失败。它不会读取 session、源码或游戏资源，也不调用 API。

失败请求的用量可能记录在后续 `output-limit-recovery` 事件中，需与原请求关联后计入一次。`missingUsage` 表示未知，零值不应自行估算；总 Token 不是计费金额，缓存计费另需供应商数据。

## 缩小窗口

用摘要中的 runId 或失败时间过滤；需要对照完整工具统计及最近 checkpoint 时才加 `-Detail`。

```powershell
.\scripts\analyze-adaptation-log.ps1 -ProjectDirectory '<项目目录>' -RunId '<runId>' -Detail
.\scripts\analyze-adaptation-log.ps1 -ProjectDirectory '<项目目录>' -Since '<ISO时间>' -Until '<ISO时间>'
.\scripts\analyze-adaptation-log.ps1 -ProjectDirectory '<项目目录>' -FromTurn 30 -ToTurn 55
```

记录调查截止时间。缺少 run-end 只说明没有观察到结束事件；不能据此断言任务还在运行。相同参数也可能在源码或输入改变后执行，判断重复应对照修改记录、结果和耗时。

`-Detail` 的 `modelTurns` 保留请求 Token、缓存与耗时；`checkpointHistory` 和 `historyCompactions` 对比压缩前后的实际请求。不能按持久化 Messages 数量判断上下文大小；旧消息为恢复而保留，不代表每轮全部发送。用量按请求归属过滤，`hostRunTokens` 则是完整运行总量；截取窗口后两者可能不同。按轮次分阶段时以实际工具和源码修改划界，重叠工作标为混合阶段；多次运行轮次可能重叠，必要时再限定 `-RunId`。

## 按调用取证

1. 从摘要挑最后一次相关验收失败、异常耗时或重复失败，用 callId 定位对应的少量 JSONL 行。
2. 日志只有元数据时，才解析一次 `adaptation/current/session.json`。优先取 `verificationDiagnostics`、`notes`、发布清单及历史位置，不输出整个对象。当前格式的完整消息位于同目录的 `session-history.jsonl`，仅逐行读取 `historyStorage.bytes` 以内的已提交内容；旧格式仍从内嵌 `messages` 取证。
3. 工具输出按调用 ID 精确查找，兼容 `toolCallId`、`tool_call_id` 和 `call_id`；参数先查 `toolCalls`，为空时从 `providerData` 中只取 `type=function_call` 的 name、call_id、arguments。Chat Completions 格式则取其 tool_calls；不要转储 reasoning、加密内容或整个 providerData。找到所需证据后停止读取历史，不把完整 JSONL 载入模型上下文。
4. 沿实际报错的文件和行号读取源码片段。需要比较产物时，在本地计算数量、ID、实际译文和未修改项差异，只返回统计及必要的少量样例，通常最多两条。不要把数万条文本交给模型比较。
5. 一次验证一个假设。超时先区分编译和运行，确认输入规模、最后输出及循环游标是否前进；仅延长超时不能证明定位正确。

用户怀疑某项检查增加消耗时，分开计算本地探针、为解决真实问题而新增的实现、重复调查及验收。一个请求包含已有上下文，整阶段 Token 不能全部归因于检查，也不能当作可节省量；不同游戏之间无受控对照时，不宣称改动导致成本上涨。先查 `largestToolOutputs` 定位大输出，再看后续输入增长、预览与定向回读，不能把原始工具输出字节直接折算成模型 Token。

调查默认只读，不干预正在运行的任务、启动游戏或触发付费 API；用户已授权的验证、修改或重跑按其范围执行。不为恢复上下文重跑已经有结果的实验。

## 核对适配结果

区分三层证据：资源可解析和往返、实际译文正确写入、原游戏运行显示。编码器与解码器共享同一个错误时也可能自洽；数量或 ID 相同不代表译文正确。原文直接复制通过不等于修改分支已被验证。同时区分**已证实出错**（译文、字形或已知结构实际损坏，必须拒绝）与**宿主验证能力缺口**（宿主不认识新尾表、新方言或新字体布局，应保留通用验收和可独立核验的证据，标注待实机确认项并放行试译，而不是把智能体卡死在“需宿主维护方补充支持”）。

检查现成解析器、组件和固定参考库是否真正试用。检索未命中应核对别名和词拆分；组件拒绝某个容器版本不能推导同引擎的脚本解析器不可用。二进制中未找到几种指令或常量，不足以排除某种能力。

压缩后再次调查同一资料时，对照压缩事件、笔记更新时间、保留的证据入口和重复调用。区分必要恢复与确实重复的探索；压缩降低请求大小与丢失关键工作事实可以同时发生，不应仅凭重复读取就取消压缩。格式或运行能力已明确但缺少可复用实现时，优先评估拆成独立可复用组件与经验线索，避免只继续追加提示词，也避免做成锁死整个引擎路线的封闭模板。

归因时考虑项目流程、任务本身的难度、模型的判断和执行能力，以及实际发生的调度或服务等待。核对关键证据是否进入了当次请求，任务目标是否明确，所需工具是否可用。条件具备时，若模型反复忽略关键结果、走错路线或无法完成必要实现，且这些行为解释了主要消耗，可以判定本轮主要受当前模型限制。评价模型本身时优先使用已有的同输入、同工具和同验收目标的对照。证据仅来自一次运行时，把结论限定在该次表现。

## 优化方案

优化目标是**减少无效摸索、沉淀可复用的底层积木与避坑线索，同时保持智能体处理未知变体的自由度**——不是替每个特定引擎直接写死“最终适配器”或封闭白名单门禁。离线静态验收无法 100% 替代实机画面，优先保证流程能顺畅抵达“通用验收通过 → 少量试译 → 实机确认与修复”的闭环。

从整体到特定引擎检查三层复用范围，每项放在证据支持的层级。按能省掉多少工作、证据有多充分，以及是否会限制未知变体自由度来排优先级，综合评估 Token、耗时与泛化能力。

- **整体（所有引擎）**。评估共用流程能否直接复用既有成果、减少模型往返、缩短调度与验收等待，或改善通用诊断与开放式证据核验（原文往返、身份稳定、独立的字体/字形自洽检查）。
- **引擎家族（积木优先于整块模板）**。依据多个引擎或版本实际共享的封包、脚本或运行暗坑，优先沉淀**正交、可单独调用的组件**（封包读写、字形/字体生成、转区启动器、代理）与结构化避坑经验，让智能体面对新变体时仍可自由组合。零 Token 组合模板只作已确认高频布局的快捷通道，未命中时必须平滑交回智能体自由调查，不得反向阻断自定义适配器。
- **特定引擎（修真暗坑，不设封闭门禁）**。针对有明确样本证据的引擎或版本，优先修复通用底层暗坑（如转区字体枚举、编码/字重陷阱、补丁恢复冲突）或补充可检索的知识线索，而不是把单个游戏的方言/配置特例硬编码进宿主强拒规则。规则以格式或行为证据为适用条件；宿主未登记的新变体应降级为带明确待确认项的开放验证，而非直接报错阻断。

优先推荐既能省去整段重复探索/返工、又不收窄智能体自由度的方案。写清收益适用于首次适配、继续适配还是工具更新后的恢复。复用已有适配结果前核对源码、输入和实际依赖。小样通过只证明对应能力可行，家族模板的收益与适用范围还需正式验收和同条件对照。只展开有证据支持的高收益方案，微调直接缓解主要瓶颈时简述。

每项写清改哪个环节、能省掉哪些工作、主要节省 Token 还是耗时，以及对未知引擎变体自由度的影响。缩减覆盖、提前交付部分支持或推迟必要验收，按交付范围或顺序的变化评估。验证收益时，在同等文本正确性、验收范围和实机要求下，对比到达同一里程碑的请求次数、Token 与墙钟耗时。有可比数据时再估算节省量。只说明会改变判断或改法的版本差异与验证限制。证据足够后结束调查。
