# Adapter CLI protocol v1

One UTF-8 JSON request is read from standard input. The adapter writes one UTF-8 JSON response to the supplied `responseFile`, or to standard output for legacy adapters. Diagnostics belong on standard error. Extensions run as local processes with the current user's permissions; API credentials are not passed in requests or inherited environment variables. Resource operations support cancellation and a ten-minute timeout; host-driven engine probes have a separate 45-second total budget. New packages have an 8 MiB stdout/stderr diagnostic limit; legacy inline responses allow 128 MiB. File responses have no fixed byte limit.

Request fields: `protocolVersion` (1), `operation` (`probe`, `extract`, `build`, `validate`), `sourceDirectory`, `outputDirectory`, `resourceFiles` (current relative candidates), optional `probeFiles`, `responseFile`, `translationsFile`, and `translations` (object mapping unit ID to translated text). When `translationsFile` is present, load that UTF-8 JSON dictionary instead of inline `translations`. These additive v1 fields preserve the existing inline request/response format used by published legacy packages.

Response fields: `protocolVersion` (1), `success` (boolean), optional `error` (string), and the operation's result under `probe`, `extraction`, `build`, or `validation`.

An optional `tools/engine-reference.json` dependency pins the shared GalTransl source library (commit and hashes) and portable Python (version and archive hash). The host resolves these files and supplies `toolPaths:{python,engineLibrary}` in the request. `use_engine_reference` creates this dependency and a framework-only `EngineReferencePython` bridge; a small `tools/*.py` wrapper implements the same JSON protocol using the upstream Python APIs. No absolute machine paths belong in the dependency or wrapper. The host uses bundled or already installed tools; missing pinned dependencies fail with a restore instruction, without automatic downloads or version substitution. Changed content is rejected. Source and license notices remain in the shared library. Python and the library stay in the application installation or shared data directory, not the game patch. These dependencies must be restored alongside a moved adapter when its destination has not cached them.

An optional `tools/vntextpatch-reference.json` records schema version 1 and content hashes for the shared VNTextPatch DLL and license notices. Binary-mode `copy_adapter` registers this dependency and a small bridge instead of copying binaries into each package. The host verifies and resolves the pinned files, provides `toolPaths.vnTextPatch`, and sets `GAMEL10N_VNTEXTPATCH` for that adapter process only. It also sets the former `AVG_TRANSLATOR_VNTEXTPATCH` variable for existing adapters, and accepts pinned `AvgTranslator.VnTextPatch.dll` dependencies without replacing their contents. The supplied bridge uses this environment path; editable source implementations take priority. Older packages with local DLLs remain supported. A transferred package requires its pinned shared files or the matching application distribution; a newer DLL must not silently replace them.

All JSON property names use camelCase. Records correspond to the documented DTOs in `src/GameL10n.Core/Contracts.cs`; generated executables define their own equivalent DTOs and have no dependency on the host assembly. A `probe` result may be null for unsupported data. Every output path is relative to outputDirectory and must stay within it. `requiredFiles` are relative to sourceDirectory and must be a nonempty subset of discovered candidates.

The optional manifest `recognition` declaration is independent of CLI protocol v1 and resource selection. It describes necessary file predicates and nonblocking hints, with its own `schemaVersion`. It does not contain execution policy. Unsupported declaration versions and unavailable evidence retain an unknown candidate for CLI probing; existing packages need no migration. Fields and matching semantics are specified in [engine recognition](../docs/adapters/recognition.md).

For manifest v2 packages, the host discovers resources from `resourcePatterns` on every game. Patterns use `/` separators, `*` and `?` within a path component, and `**` across directories; `**/*.dat` also matches root files. Probe initially receives at most 65,536 bytes from each candidate, preserving relative paths in a temporary directory. `probeFiles` entries contain `path`, original `length`, and staged `headerBytes`. Legacy manifest v1 packages retain their declared fixed `resourceFiles` and complete probe inputs.

To inspect a footer, archive index or PE resource beyond the header, return `{protocolVersion:1,success:true,probeReads:[{path,offset,length}]}` without `probe`. Only current candidate paths and valid absolute byte ranges are accepted. The host calls the adapter again locally with cumulative `probeRanges:[{path,offset,length,dataPath}]`: read `dataPath` starting at byte zero to obtain the requested slice. The original header files stay unchanged. `probeReadLimits` advertises at most 4 additional rounds, 64 ranges, 1MiB per range and 8MiB total; repeated identical requests are rejected. Batch independent reads. These are local CLI calls, not model calls; range files are temporary and checked for modification. Select the required script/font/configuration resources after inspecting indexes; avoid copying media payloads solely for discovery. Return the final `probe` or `probe:null` when finished. Existing adapters may ignore these additive fields.

Full extraction, build and validation receive host resource copies or pipeline snapshots. Adapters read these sources without changing them. The host copies original resources for verification once and checks hashes before and after each operation; it does not copy entire resources again for each CLI call. Resource copying and hashing use streams, with no per-file or aggregate byte limit.

An extract response's `extraction` contains `units` and `warnings`. Every unit has `id`, `resourcePath`, `locator`, `sourceText`, `context`, optional `speaker`, and `kind`. IDs must be unique and repeatable. Extract player-visible dialogue, narration, names, choices, UI/menu labels, items/equipment, skills/traits, tutorials and system messages when their storage and consumers are established. Suggested kinds are `dialogue`, `name`, `choice`, `ui`, `item`, `skill`, and `system`. Program instructions, internal IDs, resource paths, conditions, developer diagnostics and image/video lettering are excluded. Preserve existing unit IDs, context, kind and speaker when expanding an adapter so existing translations remain reusable.

A unit may declare `protectedTokens`, up to 64 nonempty literal markers of at most 256 characters each, all present in its source. The host masks these before translation and checks their exact occurrence counts after restoration. Declare only established runtime substitutions such as `(actionName)`, not visible parenthetical prose; declarations apply to that unit only. Changed declarations invalidate that unit's memory and edit signature. Older hosts ignore this optional field and must be updated before using adapters that require it.

Extraction and probe warnings identify observed text categories that remain unsupported. Resource roundtrip tests validate the extracted units, not whole-game text coverage. For Unity, dialogue TextAssets, serialized object fields, scene/UI components and managed/IL2CPP literals can be separate text sources. An internal object name or readable metadata string is not sufficient evidence that a field is displayed to the player.

Empty or whitespace-only display slots and spacing literals are not translation targets. Preserve their original bytes and positions in the script and omit them from extraction. For existing adapters that return them, the host validates all raw records first, then excludes whitespace-only units before verification, caching or translation. Null text, invalid resource paths and duplicate unit IDs remain errors, including on excluded records. Do not trim nonempty text, merge repeated source strings, or renumber other IDs when excluding spacing records. Builds must preserve these records when their IDs are absent from the translation map.

User-facing warnings, errors and validation issue messages use concise Chinese and give a concrete action when one is needed. Detailed disassembly and research belong in development notes.

A build response's `build` contains `files` (relative paths), `warnings`, and optional `launchExecutable`. Building with a dictionary containing all original texts must reproduce every source resource byte for byte under its original path. Translated builds also retain every source resource path and preserve non-text bytes. Additional declared outputs are allowed, including a new launch EXE. Every output must exist and every output file must be declared. A launch executable must be among those files.

When executable changes are needed, probe declares `originalExecutable` and includes it in `requiredFiles`; the host preserves it as a source resource. New or changed EXEs receive independent PE structure and applicable ASLR/relocation checks. These checks do not establish successful startup, font rendering, or game runtime behavior. A validate response's `validation` contains `passed`, `issues` (each code, message, optional unitId), and `runtimeStatus`. The host always reports `not-tested` for generated adapters.

Every validation issue is a blocking error. Success uses `passed:true, issues:[]`; a failed check uses `passed:false` with the corresponding issues. `passed:true` with nonempty issues is contradictory and rejected. Nonblocking coverage limitations, font differences and notices about untested runtime behavior belong in `probe.warnings`, `extraction.warnings` or `build.warnings`, not `validation.issues`.

The host performs independent path, hash, non-empty extraction, unique identity, roundtrip, and changed-text re-extraction checks before publishing an extension. It also builds with only a small subset of translations, re-extracts the actual output and checks every edited and untouched unit. Missing translation IDs must preserve their original text and identity. An extension cannot publish itself or claim a successful game runtime test.

New `.exe`, `.cmd`, `.bat` or `.ps1` outputs require an explicit `build.launchExecutable` pointing to a declared EXE (the original game EXE or a standalone launcher). A script alone is not a launch executable. Existing per-EXE `.le.config` profiles must be discovered and included with selected EXEs, then preserved byte for byte during translated builds. These checks detect omitted launch metadata or altered profiles; they do not prove native locale propagation, font availability or successful game startup.

Changed-text re-extraction does not establish encoding or rendering correctness when the encoder and decoder share a mapping. Adapter development must check representative translated bytes against an independent encoding reference and expected glyph bitmaps from the intended Unicode characters. Private-use remapping requires checking the shipped EXE's byte classification in both string traversal and glyph lookup. Some original System4 runtimes recognize only `81..9F`/`E0..EF` lead bytes and reject CP932 private-use `F0..F9`; `F040..F044` can then appear as `@ A B C D` even with a successful resource roundtrip. An open-source reimplementation accepting those bytes does not establish compatibility with the original EXE. Preserve the original font style by default; for GDI output, verify the selected face and required glyphs rather than relying on the requested font name or accepting silent substitution. These development checks still do not replace an actual game rendering test.

Package identity is separate from this CLI protocol. Published packages declare a family `{kind,key,name}`: kind is `engine` or `template`; key names the engine/format or a concrete structural template, never a game. The host assigns `adapterId` as `<kind>.<key>` and derives a version from source, binaries, dependencies, discovery rules and runtime. A missing family cannot be published.

New multi-file packages use manifest v3 with CLI protocol v1. One `package.json` contains `manifestVersion:3`, identity/family, `resourcePatterns`, source and assembly SHA-256 values, `packageFiles` mapping every packaged file to its SHA-256, and `releaseFiles:[{path,role,purpose}]` declaring every selected release input. `path` is a final package-relative exact file path; no directories, globs, traversal or case-insensitive duplicates. `purpose` is a nonempty explanation of at most 240 characters. Roles: `source` for `src/**/*.cs` (excluding `src/tools/`); `runtime` for `tools/**` code/dependencies; `asset` for `tools/**` data/fonts/launchers needed to build patches; `license` for `tools/**` notices/provenance or required source. Workspace `src/tools/x` maps to package `tools/x`. At least one source and at most 512 selected inputs are allowed.

The compiler requires a selection, compiles only selected sources and tests the resulting package before publication. The host persists the working selection in session.json independently of verification. test_adapter defaults to that selection; an explicit releaseFiles replaces it. update_release_files incrementally upserts/removes entries without deleting files. New C# files written under src and known built-in dependencies auto-register; other dependencies can declare releaseRole and purpose once when written/downloaded. Failures and checkpoints preserve selection. Published package reuse inherits it; legacy workspaces require an initial selection. Unselected probes, samples, reports, logs and unused tools remain in the workspace. Selected dependencies include transitive imports, native libraries, patch assets and required notices; purpose declarations do not independently prove necessity. The v3 `packageFiles` set must equal all `releaseFiles` paths plus host-generated `adapter.dll` and `adapter.runtimeconfig.json`. Host-generated `package.json` and `verification.json` are not release inputs. Roles/purposes participate in version derivation. Final sources are retained for future variant development; no analysis history is packaged. Game originals are per-game resource inputs, and modified game files are patch outputs, not reusable engine assets. The adaptation host rejects selected files whose hashes match staged game originals; this does not detect all transformed or unstaged game content. After activation, the session references the published package rather than the temporary build. No cleanup is performed. C# wrappers locate tools under `AppContext.BaseDirectory/tools`. All package files are checked on load, before execution and publication. `verification.json` is a separate host report and never replaces independent verification. Shared Python dependency pins still require the host's fixed shared toolkit.

Existing v2 manifests retain their original file/hash contract without release roles. Existing v1 manifests retain root `Program.cs` and fixed resource files. Both remain loadable without in-place cleanup. A saved pre-v3 development verification must be rerun with an explicit release selection before `finish`; existing source can be reused without repeating engine research.

Compilation accepts multiple C# files and existing tool dependencies, using the pinned .NET 10 compiler and framework references. It does not execute arbitrary project files, build tasks, analyzers or package restore. Legacy manifests with root `Program.cs`, fixed `resourceFiles`, `sourceSha256`, `assemblySha256`, and optional family continue to load with the original v1 manifest defaults.

Game titles, source hashes, resource-specific limitations and verification results belong to compatibility records under the family. Recognition of one game does not establish compatibility with other games using that engine. Reusing a generated template for a different game requires independent roundtrip verification before pinning that version. The final patch consists of game-consumable files; it has no dependency on the adapter CLI or the translator application at game runtime.
