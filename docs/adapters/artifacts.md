# 引擎分析产物与目录约定

引擎分析涉及五类文件：正式适配器、汉化运行文件、可续接的开发资料、单次执行临时文件，以及日志和全局经验。文件扩展名不能决定其用途；例如 Python 脚本既可能是分析探针，也可能是正式适配器依赖。

以下路径以应用的数据目录为起点。默认位置为 `%LOCALAPPDATA%\GameL10n`，可在“程序设置”更改。目录按需创建，不要求每个项目都具备所有文件。

## 可续接的开发资料

每个项目的当前开发目录是 `games/<项目 ID>/adaptation/current/`。

| 相对当前开发目录的位置 | 用途 | 发布时的处理 | 保留方式 |
| --- | --- | --- | --- |
| `src/**/*.py`，排除 `src/tools/` | 候选适配器的解析、提取、回填及验证代码，入口 `src/adapter.py` | 仅清单选中的文件参与语法检查、运行和发布 | 继续适配时原地修改 |
| `src/tools/**` | 适配器运行所需的脚本、DLL、EXE、配置、数据和许可声明 | 仅清单选中的文件复制到正式包的 `tools/` | 与源码一同保留 |
| `work/**` | 临时分析入口、探针、解包结果、报告和笔记 | 不打包 | 保留供继续调查和总结使用 |
| `work/status.md` | 调查状态与结论笔记，可选 | 不打包 | 恢复会话时会读取其中的有限内容 |
| `resources/**` | 从游戏选择并复制的资源、主程序、字体及转区配置等验证输入 | 不打包 | 保留，原文件哈希记录在会话中 |
| `build/**` | 最近一次打包的源码和工具依赖 | 验收通过后从这里发布 | 下次构建时替换 |
| `session.json` | 会话消息、工具结果、已确认结论、Token、覆盖范围、待办、验证状态及下一步 | 不打包 | 原子更新，供暂停、重启及继续适配恢复 |

源码位于 `src/` 不代表已发布或已验收。`build/` 也只是开发中的构建结果；会话可能引用其中已验证的包，发布前删除会影响继续发布。

文件放置遵循以下约定：

- 临时分析和处理脚本放在 `work/*.py`，由 `run_engine_python` 使用内置共享解释器运行。新正式适配器也使用 Python，通过 `test_adapter` 检查语法并执行资源验收。
- 只有适配器正常识别、提取、回填或验证需要的依赖才放入 `src/tools/`。需要随包携带的配置、数据和许可文件也放在这里；不扫描整个目录自动打包。
- 正式依赖通过包内路径定位，例如 `Path(request['adapterDirectory']) / 'tools'`，不应依赖开发时的 `work/`、`resources/` 或绝对项目路径。
- 分析笔记与工具结论优先复用已有文件，不为每次检查另建目录、备份或完整源码副本。

任务完成、失败或暂停后，`current/` 都会保留。过程资料不属于玩家的汉化运行文件，但仍可能用于继续修复、扩展覆盖或生成全局经验，不能将整个目录视为单次执行后即删除的临时目录。

## 正式适配器

正式包只保留最终适配源码、运行依赖、生成补丁必需的素材、许可与来源声明，以及宿主生成的程序和元数据。分析探针、测试入口、解包样本、报告、日志、下载压缩包和无关旧实现不应进入正式包；某种格式确实以压缩包作为运行数据时，应按实际用途声明，不按扩展名一律删除。

发布输入清单保存在 `session.json` 的 `releaseFiles` 中，与验收状态分开。验收默认使用已保存的清单，只复制和检查选中的文件，再对这份包执行完整检查。发布前再次核对选中文件和资源与验收输入一致，才激活新版本。新 Python 包使用 Manifest v4，位于：

```text
extensions/packages/<引擎或模板 ID>/<版本>/
  src/adapter.py               Python 协议入口
  src/                         其他正式 Python 模块
  tools/engine-reference.json  固定共享 Python 解释器和库
  tools/                       其他随包依赖，按需存在
  package.json                 身份、版本、资源规则、文件哈希及发布文件用途
  verification.json            宿主验收时间与诊断，运行验证单独标记
```

Python 包通过固定的共享解释器运行，不生成 `adapter.dll`。版本根据包内容、文件用途等输入生成，已发布版本固定；失败的开发任务不会替换现有激活版本。Manifest v1～v3 的旧包继续使用原 `adapter.dll` 和运行时配置，不自动改写源码或哈希；v1 可能在包根目录保留 `Program.cs`。继续修改旧包时，迁移所需逻辑为 Python，明确选择新发布文件后重新验收。为兼容历史字段，v4 的 `assemblySha256` 保存 Python 入口的哈希。

发布输入的角色和路径约定如下。路径均相对最终包，不接受目录、通配符、重复路径或越界路径。

| 角色 | 用途 | 正式包路径 | 工作区对应位置 |
| --- | --- | --- | --- |
| `source` | 最终 Python 实现，保留供复用和修复 | `src/adapter.py` 等 `.py` 文件 | `src/adapter.py` |
| `runtime` | 正常识别、提取、回填或验证需要的脚本与依赖 | `tools/parser.py` 等 | `src/tools/parser.py` |
| `asset` | 生成汉化补丁需要的启动器、字体、配置或数据 | `tools/Launcher.exe` 等 | `src/tools/Launcher.exe` |
| `license` | 依赖许可、来源或必要源码声明 | `tools/LICENSE.txt` 等 | `src/tools/LICENSE.txt` |

清单在源码编辑、组件复制和依赖登记时维护。经宿主写入的正式 Python 源码及已知必要的组件文件可以自动登记；`test_adapter` 自动准备并登记固定共享 Python 依赖。外部脚本生成的文件和间接依赖需要显式选择。未登记不代表文件可以安全删除。

清单与验收状态分开保存。重启、会话压缩和验收失败保留清单；增删发布输入后需要重新验收。旧包有清单时继承，没有清单的旧工作区需先明确选择，不能自动将历史 `src/tools/` 全部当作正式依赖。

宿主生成的 `package.json` 和 `verification.json` 不放入这份输入清单。选中的文件必须存在，所需的间接模块、原生依赖、素材和许可也应逐项声明。未选择的工作区文件不参与运行或发布，修改它们不使已通过的包验收失效；变更清单后需要重新验收。宿主校验路径、角色、文件集合及哈希，实际用途仍需结合实现核对，声明用途本身不证明该文件必需。

发布后文件角色和用途保存在现有 `package.json` 的 `releaseFiles` 中，不另建清单文件。已发布包仍须与其文件清单完全一致，不能直接删减文件；精简旧包应从现有源码重新选择、验收并发布新版本。

### 游戏文件与清理边界

原版游戏 EXE、封包和字库属于游戏输入，放在分析样本 `resources/` 或项目原文快照 `sources/`，不作为可复用引擎依赖携带。修改后的游戏程序及资源属于补丁输出。适配器保存解析和修改逻辑，从当前游戏的已校验输入生成输出；通用自制启动器、独立依赖和补丁必需字体可以作为正式素材登记。

验收及发布时，宿主比较选中文件哈希与本次暂存的游戏原文件哈希，拒绝相同副本，即使已改名。此检查只识别已登记原文件的完全相同副本，不能识别所有未暂存或已修改的游戏文件；用途声明不能替代依赖审查和当前游戏验收。

发布包可通过“全局引擎库 → 版本 → 验证发布包…”进行独立位置验收，选择一个已完成提取且当前空闲的同引擎项目。验收以现有原文快照与提取缓存为基线，不生成新的基线来掩盖遗漏；数量、文本身份及缓存字段必须保持一致。不调用模型、运行游戏或安装补丁。结果记录在所选项目的 `package-verification.json`，不写回正式包。报告仅证明记录的包、资源、基线和工具链组合通过资源检查，不自动切换版本。

手动清理前需要了解以下依赖；程序不会自动删除这些开发资料：

- 正式包是不可变版本；其中清单与哈希共同构成契约。精简旧包需要生成并验收新版本，不能原地删文件。通过引擎库删除整个版本后，它不再参与复用；原来的固定版本与回滚记录不能恢复已删除的文件。
- 发布成功后，会话中的已验收包指向正式发布目录，不再依赖 `build/` 副本；发布前的构建结果仍可能是唯一验收产物。
- `adaptation/current/` 是可续接的开发状态，即使文件未入包也不能默认删除。主动释放这些资料后，需要恢复正式源码、重新准备样本并重新验收，不能继续沿用已删除工作区的验收状态。
- `sources/` 是翻译和补丁重建的原文依据；译文、校对、安装恢复记录及备份也不属于适配器过程文件，不应随开发资料一起处理。

原文往返、中文回填与重新提取、部分试译保留原文等属于资源验收。`verification.json` 在发布时记录 `runtimeTested=false`，不证明游戏启动、字体、换行、分支和存档可用。结果含义见[智能适配](automatic-adaptation.md#验证与产物)，宿主检查及复用条件见[验收与结果复用](adaptation-internals.md#验收与结果复用)。验收样本、详细调查依据和部分待办仍主要保存在项目会话及工作资料中，正式包不包含完整调查档案。

以下全局文件与正式包相关，但用途不同：

| 位置 | 用途 |
| --- | --- |
| `extensions/catalog/<引擎或模板 ID>/games.json` | 每个游戏一条简要记录：最近使用版本、说明、结构与运行状态、更新时间；不保存资源哈希或补丁路径 |
| `extensions/games/` | 保存项目当前激活版本及上一版本的引用 |
| `extensions/library-index.json` | 引擎库展示摘要，可重建，不替代运行校验 |
| `<应用目录>/tools/engine-tools/` | 发行包附带的固定版本引擎工具库与便携 Python，直接读取 |
| `extensions/engine-tools/` | 已安装的共享工具版本、VNTextPatch 按内容哈希保存的 DLL 与许可，不逐项目复制 |
| `extensions/downloads/` | 额外工具与公开资料的共享缓存，保存 URL、内容哈希与获取时间；工作区和正式包使用独立工具副本 |

`extensions/downloads/` 可单独清理，不影响已经复制到工作区或正式包的额外工具；之后再次需要相应内容时须重新获取。它不替代适配器的发布依赖清单，也不参与适配器运行。

使用共享 Python 引擎库或 VNTextPatch 的适配器，会在包内保存固定依赖记录和调用桥，实际工具位于发行包或 `extensions/engine-tools/`。这类正式适配器并非仅复制自己的包目录就能独立执行；共享工具也不能一概视为临时下载文件。完整依赖准备方式见[智能适配](automatic-adaptation.md)。

## 汉化运行文件与补丁记录

汉化补丁位于 `games/<项目 ID>/patches/<构建标识>/`，由适配器使用原文快照和译文生成。

| 内容 | 用途 | 是否安装到游戏目录 |
| --- | --- | --- |
| 汉化资源、必要的 EXE／启动器、字体和运行依赖 | 游戏实际运行需要的文件 | 按补丁清单安装 |
| `patch-manifest.json` | 安装文件路径及哈希 | 不安装 |
| `translation-report.json` | 本次生成结果、限制和验证说明 | 不安装 |
| `translation-snapshot.json` | 本次补丁使用的译文快照 | 不安装 |

安装后的游戏只需要补丁声明的运行文件，不依赖制作工具、适配器、分析脚本或模型服务。补丁清单和报告留在项目中；安装记录保存在项目的 `installation.json`。替换游戏原文件前仍按安装规则保留 `.bak`，自动恢复需要同时保留安装记录和原文件备份；数据保存与迁移规则见[数据目录说明](../data-storage.md)。

`resources/` 中的分析样本与项目 `sources/` 中用于翻译及补丁重建的原文快照用途不同，目前可能同时保留副本。正式包发布后，项目中的 `src/`、`build/` 与全局包也可能同时存在；发布不会自动归档或删除这些开发资料。

## 单次执行临时文件

下表中的项目内路径相对 `games/<项目 ID>/`；正式包的发布暂存目录位于全局扩展目录。

| 位置 | 内容 | 正常结束时的处理 |
| --- | --- | --- |
| `adaptation/current/verification/` | 原文往返、中文修改和部分文本补丁等验收输出 | 验收退出时删除，诊断写回会话 |
| `adaptation/reuse-*`、`adaptation/reuse-check/` | 复用适配器时的资源验收工作目录 | 验收退出时删除 |
| `adaptation/run-*` | 一次适配器调用的文件头、响应、译文输入及临时输出 | 调用退出时删除，正式构建文件复制到补丁目录 |
| `adaptation/current/build.build-*`、正式包旁的 `.pending-*` | 打包或发布尚未提交的目录；旧编译流程可能留下 `build.compile-*` | 成功时移动为目标目录，正常失败时移除 |

Python 探针使用发行包中的共享解释器，不生成临时 C# 程序集。脚本自行写入 `work/` 的报告和解包文件属于开发资料，不会因本次执行结束而一并删除。

临时目录删除是尽力执行。进程被强制结束、目录不可写或文件被占用时可能残留，不能保证每次都清除；程序没有后台扫描清理历史开发目录的功能。

## 日志与全局经验

| 位置 | 用途 | 保留方式 |
| --- | --- | --- |
| 项目 `logs/adaptation-日期.jsonl` | API／工具耗时、Token、调用定位、精简结果与状态 | 按天追加，不保存成功 API 请求响应正文 |
| 项目 `logs/` 中的异常诊断 | API 异常、适配失败原因等 | 保留用于排查 |
| 项目 `engine-review.json` | 最近一次总结的结论、证据指纹、消耗和全局条目引用 | 总结时更新 |
| 项目 `logs/engine-review-日期.jsonl` | 总结的逐请求用量、上下文大小、工具定位和耗时 | 按天追加，不保存成功请求响应正文 |
| `extensions/engine-knowledge/*.json` | 同引擎适用条件、指引和可复用辅助源码 | 全局保留，按条件供智能识别选用 |

全局经验由“总结”功能产生，可以没有新增条目。它不是已验证适配器；其中的辅助源码复用到其他游戏前，仍需核对适用条件并通过该游戏的验收。

项目总结显示新增、更新或没有新增内容，并可查看适用条件、分析指引、辅助工具及其保存位置。源码保存在全局经验文件内，按需复制到适配工作区。已有报告也能查看所引用的当前经验；经验后来有更新或文件丢失时会明确提示。

证据和相关经验未变化时重复点击总结不调用模型。任务状态、界面与 API 设置不属于解析证据；更换游戏目录、资源指纹或适配器版本仍会使总结失效。已确定引擎时，无关引擎的经验更新不会触发重新总结。预算与 API 沿用智能适配配置。较大的旧工具结果按需裁剪，可取回原始结果，也可按关键词读取源码和日志。

智能识别先列出精确匹配的经验，再列出同引擎的变体线索，只提供简短索引；具体指引和辅助源码按需读取。关联只说明值得调查，不表示格式兼容，不能直接据此套用解密算法或跳过验收。

## 删除与重新开始

需要完全重新分析时，先停止任务，再手动删除对应项目的 `adaptation/current/`。这会丢失其中的会话、源码、样本和调查资料，但不会删除译文缓存、已发布适配器或已生成的补丁。只删除个别工作文件可能使恢复笔记或已保存验证引用失效。

正式适配器版本通过“全局引擎库”管理，项目历史引用不阻止删除外置版本。删除时一并移除该版本的兼容记录、全局激活引用和索引条目，不保留历史占位；已提取文本、译文和补丁仍保存在游戏项目中。需要再次提取或生成新补丁时，请重新识别或智能适配。删除整个项目数据目录会同时影响译文、原文快照、补丁与安装恢复记录，范围大于重新分析，见[数据目录说明](../data-storage.md)。
