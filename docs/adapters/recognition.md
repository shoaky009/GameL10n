# 引擎识别声明

> 完整产品的能力与协议参考；Rust 宿主的实际接入范围见[开发文档](../development.md)。

常规识别和智能适配的已有能力检查共用一条路径：扫描游戏目录一次，从引擎索引筛选文件规则，按需读取字节签名，再执行少量候选的 CLI `probe`。完整提取和跨游戏回填验收在匹配之后执行。

## 包清单

`package.json` 的可选 `recognition` 字段声明静态事实。它独立于 CLI `protocolVersion`、发布文件 `releaseFiles` 和资源选择 `resourcePatterns`：

- `resourcePatterns`：选择交给适配器的资源，多个模式取并集，不表示每个模式都必须命中。
- `recognition.required`：已证实的必要条件，所有规则都必须满足，才能确认匹配。
- `recognition.hints`：辅助证据，只影响主程序排序，缺失或不符不排除适配器。
- `probe`：解析容器目录、脚本版本或其他自定义结构，最终决定是否匹配及必需资源。

```json
{
  "schemaVersion": 1,
  "required": [
    {
      "patterns": ["**/*.pak", "**/*.arc"],
      "minimumSize": 16,
      "signatures": [
        { "origin": "start", "offset": 0, "hex": "5041434B" }
      ]
    }
  ],
  "hints": [
    { "patterns": ["engine.ini"] }
  ]
}
```

此例表示至少有一个 PAK 或 ARC 文件，长度不少于 16 字节，并且以 `PACK` 开头。它仅用于说明协议，不代表任一实际引擎。

每条文件规则中，`patterns` 是可替代的路径模式，任一命中即可；大小和全部签名必须在同一个文件上满足。路径为相对游戏根目录的 `/` 路径，不区分大小写，支持 `*`、`?` 和 `**`；`**/` 也可以匹配根目录。没有大小或签名约束时只判断文件存在。

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 当前为 `1` |
| `required`、`hints` | 必须提供，可以为空数组；合计最多 32 条规则 |
| `patterns` | 每条规则 1～16 个非空路径模式，不允许绝对路径或目录穿越 |
| `minimumSize`、`maximumSize` | 可选，原始文件的非负字节长度范围，包含边界 |
| `signatures` | 可选，每条规则最多 8 个，全部匹配 |
| `hex` | 1～64 字节，连续偶数长度十六进制，无空格或通配字节 |
| `origin` | 默认为 `start`；也可为 `end` |
| `offset` | 非负字节偏移。`start` 从文件开头到签名起点；`end` 从文件结尾向前到签名终点。`end, offset:0` 表示文件最后几个字节 |

不得把单款游戏的标题、安装路径、整包哈希或未经证实的惯用文件名设为引擎必要条件。规则没有脚本、下载、进程、排名权重或时间预算字段；这些属于主程序执行策略。

## 发布与兼容

`test_adapter` 可附带 `recognition`。提供时替换保存的声明，省略时复用；提供空 `required`、`hints` 可以清空条件。声明随任务状态保存，不要求每次重填。必要条件必须在真实游戏上全部确认后才允许通过验收；读取失败或预算不足不能据此宣告验收通过。辅助线索可以缺失。声明参与包版本指纹，正式发布版本保持固定。

旧适配器无需修改或重新发布。没有声明时，主程序仍利用原有资源规则筛选和排序，再保留深入探测兜底。识别结果分为匹配、不匹配、未知；缺少声明、不支持的声明版本、文件不可读或达到读取预算都保留为未知。只有充分检查后确定不满足的必要条件才排除候选。

`recognition.schemaVersion` 独立演进。后续主程序的缓存、排序或并发策略调整不改变此协议；未知声明版本按未知处理，继续 CLI 探测。CLI v1、包清单 v1～v3 和现有文件布局保持兼容，不对历史包执行迁移。

## 主程序索引与执行

`extensions/library-index.json` 保存可重建的识别摘要，发布时同步写入，启停、回退和删除沿用引擎库管理规则。旧索引首次识别时只补读包元数据并导入旧激活记录，后续不逐项目扫描激活文件。候选真正执行前才加载正式包并检查完整性；摘要不授权代码执行。索引缺失时从注册数据重建，不读取所有 DLL 或游戏资源。

每次显式识别创建新的目录和文件片段缓存，结束后释放；提取、构建及补丁验收不复用该扫描结果。原始签名读取总量、候选排序和超时均由主程序限定。当前签名与文件头缓存最多 8 MiB、512 次读取；单条规则最多检查 128 个候选文件，未检查部分保留未知。文件头缓存只共享内存内容，各适配器仍获得独立的输入目录并检查修改。外置适配器探测总预算为 45 秒，完整提取、构建和校验仍使用原有预算。

## 常规识别日志

选中游戏项目后，点击“打开日志目录”，在当天的 `yyyyMMdd.log` 中搜索 `[识别诊断]`。日志自动记录，无需启用调试开关。每行包含本次任务的 `runId`、时间和 `entry`；`analysis-run` 还记录程序构建标识，用于区分版本和多次识别。

`candidate-start` 在加载候选前写入，包含适配器 ID、版本及入选依据：项目固定版本、内置自检、识别声明匹配，或仍需探测的未知候选。外置候选附带资源模式、证据分数和声明规则数；`probe-resources` 记录内置脚本工具实际按扩展名或伴随文件选中的输入。资源摘要包含文件数、总字节数及最大的 5 个文件，不读取或记录正文；`complete=false` 表示扫描或文件大小信息不完整，不能把总量当作完整统计。

`probe-result.matched` 表示探测是否匹配；`reuse-candidate.accepted` 才表示候选最终可用。探测通过后仍可能在提取或回填验收中失败。内置解析失败会附带简短诊断，外置回填结果记录在 `verification-result`。

`discovery-phase`、`candidate-phase`、`analysis-phase` 和 `verification-phase` 分别记录筛选、候选检查、项目快照与提取、回填验收的步骤。步骤先写 `status=started`，结束时写 `completed`、`failed` 或 `cancelled` 及 `elapsedMs`；已知输入上的不匹配或验收未通过需结合上述结果事件判断，`completed` 仅表示该操作执行完毕。哈希、快照复制与复制后的校验、提取缓存、实际提取、原文与中文及局部回填分别计时；不小于 64 MiB 的文件还单独记录路径、大小和哈希／复制耗时，避免逐个展开小文件。`extraction-result.cached` 表示是否复用已保存文本。

常规识别在阶段开始记录写入日志后才开展该步骤。排查运行中的停顿时，按 `runId` 查找最后一条尚无结束记录的步骤；进程退出或日志不完整也可能留下开始记录，不能仅凭它断定任务仍在运行。
