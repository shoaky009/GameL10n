# 适配器如何参与游戏识别

## 识别流程

新发布的适配器会在包清单中写入 `discoveryIndexVersion: 1`，参加以下筛选。旧版本沿用原来的资源匹配和探测流程。

1. **查索引。** 主程序扫描游戏目录，用文件名和扩展名在适配库索引里查候选。一个必要条件有多个备选模式时，任一模式命中都会进入下一步。
2. **核对必要条件。** 主程序检查文件路径、大小和声明的签名。同一次筛选共用相同规则的结果。只有能确认必要条件不成立时才据此排除。目录扫描不全、签名读不到或超过读取预算时保留候选。
3. **运行适配器。** 常规识别优先尝试当前项目固定或曾通过验收的版本。其余符合复用条件的候选依次执行 `probe`，匹配后再提取并验收。智能适配的自动探测沿用相同的筛选逻辑，也可以按名称搜索其他发布版本作为源码参考。

旧包缺少识别声明时，仍可用已有资源路径或模式筛选。只声明 `*.exe` 的旧包遇到包含 EXE 的游戏时，会保留实际探测机会。因此耗时取决于筛选后仍需探测的版本数。[候选索引](../../crates/core/src/catalog/routing.rs) · [探测与验收](../../crates/engines/src/service/discover.rs)

## 包清单

`resourcePatterns` 选择资源。可选的 `recognition` 以独立的 `schemaVersion: 1` 声明静态证据，最终适用性由 CLI `probe` 确认。

```json
{
  "schemaVersion": 1,
  "required": [{
    "patterns": ["**/*.pak", "**/*.arc"],
    "minimumSize": 16,
    "signatures": [{ "origin": "start", "offset": 0, "hex": "5041434B" }]
  }],
  "hints": [{ "patterns": ["engine.ini"] }]
}
```

- `required` 的每条规则都需命中。同一条规则的路径、大小和全部签名须由同一文件满足。
- `resourcePatterns` 是适配器可能用到的全部文件。需要读取 EXE 或字体时，将脚本或封包的必要特征单独写入 `required`，让主程序在启动适配器前排除不相关的游戏。
- `hints` 只影响排序。证据不可读或版本未知时，候选仍可进入探测。
- 路径相对游戏目录，忽略大小写。使用 `/`，支持 `*`、`?` 和 `**`。`**/*.pak` 也匹配根目录。
- `signatures` 使用十六进制字节。默认 `origin: "start"`，`offset` 从文件头量到签名开头。用 `"end"` 时从文件尾量到签名末尾。
- 规则以格式证据为依据。大小边界可通过 `minimumSize` 和 `maximumSize` 指定，均包含边界。

向 `test_adapter` 提交 `recognition` 会替换声明，省略则复用。发布时声明参与版本校验。[字段校验](../../crates/engines/src/discovery.rs) · [适配工具接口](../../crates/engines/prompts/adaptation-tools.json)

## 常规识别日志

项目日志中的“筛选出 … 个扩展适配器候选”记录静态筛选后的数量。“正在检查 …”表示已进入该版本的探测流程。资源不兼容时会继续尝试其他候选，缺少工具或完整性检查失败时会显示错误。
